## Problem Statement
- What needs to change and why: Phase 1 factory tickets (#333 personas/skills, #334 Confidential K8s + secrets, #335 OpenHands + LiteLLM, #336 GitHub Actions webhooks) each depend on ten architectural decisions that have been pinned in initiative memory but never written as `Status: approved` ADRs. Without that written record, Phase 1 implementers either (a) re-derive each decision from prose in the issue bodies (drift risk), (b) wait for sign-off cycles on per-ticket micro-decisions (velocity loss), or (c) ship implementations against assumptions that are later overridden (rework). The same window also requires three observability prerequisites: the two-layer CODEOWNERS that governs the first factory `agent-ready` label (compliance-critical the moment the factory opens its first Draft PR); the success-metric instrumentation plan that pins the durable-bus emission contract pinned by #339 FR-010 and selects a concrete STACKIT-managed platform; and the pre-factory baseline measurements + triage+decomposition data feed that make Phase 1 "did the factory help?" answerable and Phase 3 (#338) composition orchestration designable against evidence rather than assumption. This work item produces all of those artifacts in one signed-off PR and reciprocally resolves #339 Open Decisions Q-2 and Q-3 in the same PR cycle.
- Scope boundaries: this work item produces the meta-ADR at `docs/blueprint/architecture/decisions/ADR-issue-337-factory-phase-0-foundations.md`, ten content ADRs (FR-001 through FR-010) under the same directory, three documents under `docs/blueprint/autonomous-factory/` (instrumentation-plan.md, pre-factory-baselines.md, triage-decomposition-data-feed.md), the populated `.github/CODEOWNERS`, reciprocal edits to `docs/blueprint/autonomous-factory/design-contracts.md` (C6/C7 `### Blueprint instance`, C7 `### Open Decisions`, C8 ADR enumeration), the `blueprint/contract.yaml` `template_sync_allowlist` extension for the three new autonomous-factory documents, the bootstrap template mirror sync, and an empty `.agents/personas/consumer/.gitkeep` per #339 FR-018 namespaced discovery convention.

## Risks and Tradeoffs
- Risk 1 — Open Decisions backlog (seven questions Q-1 through Q-7 surfaced in spec.md). Until resolved, AC-001, AC-002, AC-003, AC-004, AC-005 cannot be fully satisfied. Mitigation: every question carries an Agent recommendation with rationale; six of the seven have a clear Option A path with documented tradeoffs; Q-3 (CODEOWNERS team provisioning) is the only question whose answer depends on real-world action (GitHub team creation by the user). Worst-case parking strategy: Q-3 Option C (ship slug names, defer team provisioning under `### Open Decisions`) preserves AC-001 through AC-005 while making the team-provisioning gap explicit.
- Risk 2 — Sign-off concentration on a large PR: ten ADRs + CODEOWNERS + three autonomous-factory documents + #339 design-contracts.md edits + bootstrap mirror + `template_sync_allowlist` change is a large review surface. Mitigation: this is identical in scope to #339 (which signed off in 24h); the ten ADRs are short (each is one decision); the three autonomous-factory documents are structured (instrumentation plan ≤ 200 lines, baselines ≤ 100 lines, data feed = a Markdown table); reviewers can read by family (Architecture reads ADRs, Operations reads instrumentation plan + baselines, Security reads FR-003/FR-004/FR-005 trio); NFR-REL-001 independence makes per-family revert tractable.
- Risk 3 — Triage+decomposition data feed sample size (Q-7): if fewer than 30 ticket cycles exist within the Q-6 measurement window, the data feed may be statistically weak. Mitigation: Q-7 Option A (use whatever count is available with an explicit `### Sample Size` caveat) preserves AC-005 satisfaction; #338 design treats the feed as directional rather than statistical; the alternative (defer FR-015 until 30 cycles accumulate post-Phase-0) removes evidence input from #338 design entirely, which is worse than weak evidence.
- Risk 4 — Pre-factory baseline window cutoff (Q-6): choosing all-time SDD-era (Option A) means baseline includes early-SDD-era PRs that may behave differently from steady-state. Mitigation: Option A is the most faithful comparand for "what was the factory replacing"; statistical noise from early-SDD-era is mitigated by reporting median/P50 rather than mean (FR-012(a) primary metric is P50 explicitly).
- Risk 5 — Durable-bus availability spike (Q-5): the FR-013 platform pick depends on `stackit_kafka_instance` being provider-stable. If the spike fails Option A, the pick shifts to Option B (SKE-hosted Strimzi), which adds K8s operational ownership to Operations and is a different blast radius than the originally framed managed-service choice. Mitigation: the spike is bounded to 1 day per Q-5 Agent recommendation; the fallback chain A→B→C is explicit; if Option C (RabbitMQ) becomes the pick, the C7 `### Identical rule` interpretation shifts from log-based replay to queue-based redelivery and requires a #339 amendment in the same PR cycle.
- Risk 6 — Reciprocal #339 design-contracts.md edits create a circular sign-off dependency: this work item edits a document that already carries the #339 sign-offs. Mitigation: the edits are scoped to subsections (C6 `### Blueprint instance`, C7 `### Blueprint instance`, C7 `### Open Decisions`, C8 ADR enumeration) that #339 explicitly deferred to this work item; the edits do not re-litigate the `### Identical rule` content; the four sign-offs on this work item cover the deltas without re-opening #339.
- Tradeoff 1 — One PR vs ten ADR PRs (selected: one PR per OPTION_A in spec.md). Pro: one sign-off cycle, one rollback envelope, one bootstrap mirror sync, one `template_sync_allowlist` change. Con: concentrated review burden. Accepted mitigation: per-artifact revertibility (NFR-REL-001) + the #339 precedent demonstrating sign-off velocity at this scope.
- Tradeoff 2 — Concrete numeric thresholds (Q-1, Q-2) vs deferred numeric thresholds: chose concrete (Option A in each question) because FR-015 retrospective classification requires the thresholds to exist. Pro: AC-005 satisfiable in this PR. Con: thresholds are best-guess and will require Phase 1 evidence-based amendment. Accepted mitigation: each ADR is independently amendable post-merge under the same sign-off process.
- Tradeoff 3 — CODEOWNERS team provisioning before or after this PR (Q-3 Options A vs C): chose conditional-on-user-action (Option A if user provisions teams in time, otherwise Option C). Pro: AC-002 is the only AC sensitive to this choice and Option C still preserves it via a documented deferral. Con: if Option C is exercised, the first factory `agent-ready` label cannot be applied until the deferred provisioning completes. Accepted mitigation: the deferral is recorded in CODEOWNERS comments and in #339 C6 `### Blueprint instance` so future readers know the gating condition.
