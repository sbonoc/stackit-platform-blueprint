## Problem Statement
- What needs to change and why: the four Phase 1 autonomous-factory tickets (#333 personas, #334 Confidential K8s, #335 OpenHands+LiteLLM, #336 webhooks) and the Phase 0 sibling #337 all depend on the same cross-ticket conventions (branch naming, spec directory layout for decomposed work, persona↔microagent mapping, integration AC format, factory bot identity + SoD detection, CODEOWNERS team slugs, metrics dashboard target + event schema). Without one pinned source, each ticket invents its own values for the same shared concepts and Phase 1 ships with inconsistent assumptions discovered only at integration time. The two failure modes already foreseeable are: (1) #335 and #336 disagreeing on branch and spec paths; (2) #333 persona DoDs referencing a bot identity #334 has not provisioned; (3) #337 populating CODEOWNERS with team names #336 does not know to allowlist. A third class of failure mode emerges because the factory is not blueprint-only: the blueprint ships the factory as a capability for consumer repos to instantiate per-consumer (own Confidential K8s cluster, own OpenHands deployment, own GitHub App, own bot identity, own CODEOWNERS, own dashboard); without a parameterized profile that separates identical conventions from per-consumer values, consumer repos either copy the blueprint's literal values (wrong tenancy) or invent their own conventions (drift). The design-contracts document therefore declares C1–C4 as identical conventions, C5–C7 as parameterized (identical rule + blueprint instance + consumer overlay schema), and C8 as the enumerated consumer-shipped surface (docs/ADRs, module wrappers, make targets + skill runbooks, GitHub App / workflows; LiteLLM excluded as pre-existing external service).
- Scope boundaries: this work item produces exactly two new artifacts — the design-contracts document at `docs/blueprint/autonomous-factory/design-contracts.md` and one summary ADR at `docs/blueprint/architecture/decisions/ADR-issue-339-factory-design-contracts.md`. The contracts pinned are the eight listed in the spec (C1–C8).
- Out of scope: implementation of any contract (CODEOWNERS population, bot provisioning, event emission, persona file creation, module wrapper authoring, make target implementation, skill runbook authoring, GitHub App manifest provisioning, etc.); enumeration of concrete bounded contexts beyond a placeholder structure; #337's own ten ADRs; any change to existing `docs/blueprint/contracts/` or `docs/blueprint/governance/` documents; concrete per-consumer values for C5/C6/C7 overlays (those are owned by each consumer repo's own factory-onboarding work).

- Context A — Factory Governance (this work item): owns cross-ticket interface conventions for the autonomous software factory AND the consumer-shipped surface schema. Surface: the design-contracts document and its summary ADR. Editorial authority: Architecture, with Security and Operations co-signing.
- Context B — Phase 1 implementers in the blueprint repo (downstream): #333, #334, #335, #336 own implementation of the contracts inside the blueprint's own factory instance and own authoring of the module wrappers / make targets / skill runbooks / GitHub App manifest that Contract C8 enumerates as the consumer-shipped surface. They MUST NOT redefine values pinned in Context A; they MAY surface deltas via PR comments that update Context A.
- Context C — Phase 0 sibling #337: depends on Context A for CODEOWNERS team slugs (Contract C6 blueprint instance), bot identity SoD rule (Contract C5 identical rule), and event schema (Contract C7 identical rule). #337's own ADRs are not Context A's responsibility; the dependency is unidirectional.
- Context D — Consumer repos as factory-instance owners: each consumer repo that adopts the autonomous factory operates its own per-consumer factory instance (own Confidential K8s cluster, OpenHands deployment, GitHub App installation, bot identity, CODEOWNERS, dashboard) by inheriting the surface enumerated in Contract C8 via the existing blueprint `contract.yaml` mechanism. Consumer repos MUST apply C1–C4 identically and MUST populate their own values into the C5/C6/C7 `### Consumer overlay` schemas. They MUST NOT inherit the blueprint's literal values for C5/C6/C7. Editorial authority for each consumer's own values lies in that consumer repo; this work item is forbidden by FR-016 from carrying concrete consumer-specific values. Additionally, Context D consumers MAY author their own personas, skills, and SDD steps under the namespaced subdirectory convention pinned by FR-018 (e.g., `.agents/personas/consumer/`, `.agents/skills/consumer/<name>/`, `consumer-sdd-stepXY-<name>`), and MAY shadow `extensible`-tier blueprint artifacts by placing same-named files in the consumer namespace; shadow attempts against `sealed`-tier artifacts (FR-017(b)) MUST be rejected by the OpenHands loader at startup. Consumer-authored extensions MAY carry `upstream-candidate: true` in front-matter to signal upstream-contribution intent (FR-020); blueprint maintainers carry no obligation to accept them.

## High-Level Component Design
- Domain layer: governance content — the eight contract sections C1–C8. Each section is self-contained and addressable by section anchor. C5–C7 each decompose into the three required subsections `### Identical rule`, `### Blueprint instance`, `### Consumer overlay`. C8 enumerates the consumer-shipped surface in four named categories (docs/ADRs, module wrappers, make targets + skill runbooks, GitHub App / workflows) and additionally carries (a) the orthogonal extensibility-tier dimension (FR-017: `sealed` / `parameterized` / `extensible`, default extensible, sealed list pinned to compliance items only), (b) the consumer-extension discovery convention based on namespaced subdirectories (FR-018), (c) the semver-style compatibility posture for the factory contract version (FR-019), and (d) the `upstream-candidate: true` front-matter convention (FR-020).
- Application layer: none (documentation-only).
- Infrastructure adapters: none.
- Presentation/API/workflow boundaries: the deliverable surfaces through the existing `docs/blueprint/` rendering pipeline (`make docs-build` / `make docs-smoke`). The ADR surfaces through the same pipeline at the conventional ADR path. Consumer-side inheritance surfaces through the existing blueprint `contract.yaml` mechanism (no new inheritance machinery introduced — see FR-015).

## Non-Functional Architecture Notes
- Security: Contract C5 specifies the deterministic factory-bot identity rule used by multi-author SoD detection. The rule MUST use exact-string equality on the GitHub login; substring or regex heuristics MUST NOT be used (NFR-SEC-001). The rule applies identically to every factory instance — the blueprint's instance and each consumer instance — with each instance carrying its own bot login per the C5 `### Consumer overlay` schema. No secrets or credentials live in this document; LiteLLM access keys (introduced by C8 / FR-014) are referenced by ESO binding, never inlined.
- Observability: Contract C7 defines the minimum lifecycle-event field set. The schema must be expressed in a form downstream consumers can adopt without re-specification (NFR-OBS-001). Eight fields are required: `ticket_id`, `parent_ticket_id`, `phase`, `persona`, `model`, `timestamp`, `outcome`, `rerun_round`. The identical rule applies to every factory instance; per-instance dashboards target whatever platform that instance declares in its C7 `### Consumer overlay` schema field.
- Reliability and rollback: rollback for this work item is reverting the design-contracts.md change in isolation. No runtime code depends on the document's contents at runtime; downstream tickets adopt values during their own implementation. `Referenced by:` lines per contract section make blast radius explicit (NFR-REL-001). Consumer-side rollback is identical — consumers depend on the surface enumerated in C8, and reverting this document invalidates their inheritance contract until restored.
- Monitoring/alerting: no runtime monitoring introduced. Documentation drift is caught by `make docs-build` and `make docs-smoke` (NFR-OPS-001) at the next PR that touches related docs.
- STACKIT-managed and local-first preconditions for C8 surface: every module wrapper enumerated under Contract C8 (Confidential K8s cluster, OpenHands deployment, ESO bindings, webhook receiver) MUST default to STACKIT-managed runtimes (SDD-C-013) and to local-first execution under `docker-desktop-preferred` (SDD-C-014); the C8 enumeration schema MUST carry both properties as preconditions of inclusion (NFR-OPS-002). Per-wrapper realization remains owned by #334/#335/#336 inside the blueprint and by each consumer's onboarding in their own repo.
- Compatibility posture (FR-019): the factory contract version follows semver. Breaking changes (removed fields, renamed identifiers, changed semantics on `sealed` items) MUST be batched into major releases with migration notes; additive changes (new fields, new artifacts, new tiers added to `extensible` items) ship as minors; bug fixes as patches. The supported-major window (whether N-1 majors are co-supported with N and for how long) is owned by #342 (Phase 1 factory upgrade process; Q-5 resolved) — not pinned here.
- Extensibility posture (FR-017): consumer freedom is prioritized over centralized audit guarantees. Default tier is `extensible`; `sealed` is reserved for the explicit FR-017(b) compliance list (bot-identity exact-string rule, four canonical sign-off phrases, multi-author SoD rule, sovereignty/ZDR ADR, reject-rerun cap rule, C7 minimum lifecycle-event field set). Consumers may shadow `extensible` artifacts in the consumer namespace (FR-018), creating per-consumer review or implementation behavior; the audit story for cross-consumer review consistency is intentionally relaxed in exchange for blocking the fork-or-stagnate failure mode.

## Risks and Tradeoffs
- Risk 1 — Open Decisions backlog: three blueprint-instance values (C5 bot handle, C6 team slugs + bounded contexts, C7 dashboard platform) carry deferred resolution to #334/#337, plus one new question (Q-4 LiteLLM access field name in `contract.yaml`) resolves during deliverable authoring. If the downstream tickets close before resolving them, dependents will adopt placeholders. Mitigation: each open decision names the deferring ticket and is gated as a non-closure condition on that ticket; AC-004 enforces this in the document; spec sign-off acknowledges the deferral path. Q-4 is enforced as a pre-SPEC_READY gate (not deferred to a downstream ticket).
- Risk 2 — Document churn during Phase 1: as #333–#337 implement the contracts they may surface deltas requiring spec amendments. Mitigation: each contract section is independently editable; `Referenced by:` lines localize the impact; amendments follow the same SDD/sign-off flow as the original document.
- Risk 3 — Per-consumer drift via incomplete overlay schemas: if the C5/C6/C7 `### Consumer overlay` subsections under-specify (e.g., missing validation rule, ambiguous configuration location), consumer repos will invent their own conventions and reintroduce the very drift this work item prevents. Mitigation: FR-016 requires schema-level precision (field name + type + configuration location + validation rule); AC-008 enforces presence and shape; per-consumer values are forbidden from this document so the schema is the only inheritance contract.
- Risk 4 — Consumer-shipped surface stability (Contract C8): consumers depend on Make targets, skill runbooks, module wrappers, and the GitHub App manifest enumerated by C8. Any breaking change to the shape of those surfaces is a multi-consumer migration. Mitigation: FR-015 requires each enumerated surface item to declare a stability tier (`stable`, `preview`, `internal`); FR-019 pins a semver-style factory contract version with breaking changes only at major boundaries; supported-major window and migration tooling are owned by #342 (Phase 1 factory upgrade process; Q-5 resolved).
- Risk 5 — Audit-consistency erosion from extensible-shadow rights: because FR-017 defaults to `extensible` and only the FR-017(b) compliance list is sealed, two consumer instances can answer "what does step08 review look like?" with very different outputs (one may shadow `security-reviewer.md` with a domain-specific replacement). Mitigation accepted: cross-consumer review-output consistency is intentionally not a goal; the audit guarantee is scoped to FR-017(b) sealed items only; the loader's sealed-shadow rejection rule (FR-018) prevents accidental compliance erosion. The risk is documented so future Phase 0 ADRs can revisit the sealed list if new compliance regimes apply.
- Tradeoff 1 — single-file vs many-ADRs: chose single-file (per OPTION_A in spec.md). Pro: one place to read, easier cross-references, fewer sign-off cycles. Con: any contract amendment touches the same file (cosmetic blast-radius). Mitigation accepted: per-section `Referenced by:` lines make true blast-radius visible at review.
- Tradeoff 2 — strict normative language in a governance doc: governance prose typically uses softer wording. We constrain ourselves to `MUST/MUST NOT/SHALL/EXACTLY ONE OF` per `AGENTS.md § Normative Language Policy`. Pro: removes interpretive drift across implementer agents. Con: prose reads as terse; informative context lives in dedicated non-normative sections of the deliverable.
- Tradeoff 3 — parameterized profile (C5/C6/C7) vs separate consumer-side doc: chose parameterized subsections inside C5/C6/C7 plus a dedicated C8 surface contract. Pro: the parameterization is visible alongside the rule it parameterizes, the consumer-inheritance mechanism is enumerated in one place. Con: contract sections become longer and contain three subsections each. Mitigation accepted: the three subsection names are mandated by FR-008/FR-009/FR-010 and validated by AC-008 so structure remains uniform.
